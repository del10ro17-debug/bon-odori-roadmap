## 6. grader.py との対応

| 設定 | 原価への影響 |
|------|-------------|
| `grading_mode=rich`（UIデフォルト） | 出力5k〜12k tokens + high image |
| 小5-6 → `OPENAI_PRECISE_MODEL` | gpt-4o/5 の高単価 |
| `image_detail=high`（rich時） | 1枚 +1,000〜1,800 input tokens |
| `max_output_tokens=14000` | 見開き25問で出力上限まで使うと最大コスト |
| `simple` + low detail | **S4: 最安（でも親体験はリッチより劣る）** |
| 解答ページ `answer_key` 添付 | 画像+1枚分。読み取り精度↑、解く必要↓（出力はやや減） |

## 7. 現行モデルを維持した場合の含意

親の手入力なし（今の設計）を守る = **Vision LLM 従量は避けられない。**

| やること | 現実性 |
|----------|--------|
| リッチのまま月980円 | 50回なら**ギリ可** / 80回は**不可** |
| リッチ80回の損益分岐月額 | **約1,600円**（19.7×80） |
| 見開き25問が多い家庭 | **39.6円/回** → 月50回で2,000円 |
| お手軽デフォルト + リッチ都度 | **ギリ可能** |
| 回数上限30 + お手軽 | 月980円で粗利数百円 |
| コード最適化のみ（モデル据置） | **10〜20%削減**程度 |

**「UXそのまま」で原価を1/10にする魔法はない。** 下げられるのは:
- お手軽をメインにする（解説は別課金）
- 1撮影あたりの問題数を減らすUX（大問分割）
- 出力トークン上限の厳格化
- 再撮影・失敗リトライの削減
